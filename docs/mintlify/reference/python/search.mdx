## Search

Payload for hybrid search operations.

Can be constructed by directly providing the parameters, or by using the builder pattern.


### Local Search

`PersistentClient`, `EphemeralClient` and the single-node server (`chroma run`) run Search as distributed Chroma runs it once a collection is compacted: the same rank expressions (dense and sparse `Knn` leaves, arithmetic, `Rrf`), `default` and `return_rank`, `where` on metadata, IDs and documents, `group_by`, `limit` and `select`, with the same scores.

For example, with the embedded Python client:

```python
import chromadb
from chromadb import K, Knn, Search
from chromadb.api.types import Schema, SparseVector, SparseVectorIndexConfig

client = chromadb.EphemeralClient()
schema = Schema()
schema.create_index(key="sparse", config=SparseVectorIndexConfig(bm25=False))
collection = client.create_collection(
    "local-sparse-example", schema=schema, embedding_function=None
)
collection.add(
    ids=["match", "disjoint"],
    embeddings=[[1.0, 0.0], [0.0, 1.0]],
    metadatas=[
        {"sparse": SparseVector(indices=[1], values=[2.0])},
        {"sparse": SparseVector(indices=[9], values=[1.0])},
    ],
)
result = collection.search(
    Search().rank(Knn(
        query=SparseVector(indices=[1], values=[1.0]), key="sparse", limit=2
    )).select(K.SCORE)
)
assert result["ids"] == [["match"]]
assert result["scores"] == [[-1.0]]
```

What follows from the single-node architecture:

- Dense `Knn` leaves read the local HNSW index, the same as `query()`, so they are approximate as `query()` is. A single node has no SPANN index.
- Sparse `Knn` leaves are exact and score `1 - dot(query, record)`. Only records that share at least one dimension with the query are candidates, as with the sparse index of a compacted collection in distributed Chroma: records with an empty or disjoint sparse vector, and records missing the field, are excluded. With `bm25` on the sparse index of the key, the query is weighted by IDF as in distributed Chroma: every weight times `ln(1 + (n - n_t + 0.5) / (n_t + 0.5))`, where `n` is the number of records of the collection and `n_t` the number of records whose vector has the dimension.
- Every read level returns the same records: a single node indexes each write before acknowledging it.
- Equal scores come in the order the records were stored.

Each request reads from one SQLite snapshot after the normal local backfill; it does not provide a transaction spanning separate client calls.

## Select

Selection configuration for search results.

Fields can be:
- Key.DOCUMENT - Select document key (equivalent to Key("#document"))
- Key.EMBEDDING - Select embedding key (equivalent to Key("#embedding"))
- Key.SCORE - Select score key (equivalent to Key("#score"))
- Any other string - Select specific metadata property

Note: You can use K as an alias for Key for more concise code.

## Rrf

Reciprocal Rank Fusion for combining ranking strategies.

RRF formula: score = -sum(weight_i / (k + rank_i)) for each ranking strategy
The negative is used because RRF produces higher scores for better results,
but Chroma uses ascending order (lower scores = better results).

## Group By

### GroupBy

Group results by metadata keys and aggregate within each group.

Groups search results by one or more metadata fields, then applies an
aggregation (MinK or MaxK) to select records within each group.
The final output is flattened and sorted by score.

## SearchResult

Column-major response from the search API.

Searches are performed in batches. Each batch is a list of records in columnar form.

```python
results = collection.search([search_1, search_2, ...])
payloads = zip(results["ids"], results["documents"], results["metadatas"])
```

Each payload contains a field grouped per search payload, in column-major form.

```python
for payload in payloads:
    ids, docs, metas = payload
    for id, doc, meta in zip(ids, docs, metas):
        print(id, doc, meta)
```
